On 2026-09-11 the user asked for (1) Google login and (2) an audit that user data on Neon is properly compartmentalized per user. See [[project_backend_migrated_to_neon]] for the wider backend context this builds on.

**Audit result: isolation was already correctly implemented, no fix needed.** Neon has no RLS / `auth.uid()` equivalent, so isolation is enforced entirely in the API layer: `requireUser()` (`api/_lib/auth.js`) extracts `userId` only from the verified JWT's `sub` claim, never from the client payload; every multi-tenant query in `api/sync/pull.js`, `api/sync/push.js`, `api/push/subscription.js`, `api/user/dog-events-reminder.js` filters/inserts on that `userId`; every child table in `db/schema.sql` carries `user_id ... references users(id) on delete cascade`. This pattern was already documented in `db/schema.sql`'s header comment — confirmed still accurate by reading every handler, not just trusting the comment.

**Added: Google Sign-In (`api/auth/google.js`)**, additive to the existing magic-link flow, not a replacement:
- Verifies the Google ID token (GIS `credential`) using **`jose`'s `createRemoteJWKSet` against Google's JWKS** (`https://www.googleapis.com/oauth2/v3/certs`), not the `google-auth-library` package — `jose` was already a dependency, avoids adding a new one. Checks issuer + `audience: GOOGLE_CLIENT_ID` + requires `email_verified`.
- Account linking: looks up by `users.google_sub` first (returning user); if not found, `insert ... on conflict (email) do update set google_sub = ...` — so a Google login with an email that already has a magic-link account attaches to that same account instead of creating a duplicate (data isolation stays 1 person = 1 `users` row = 1 set of pets). Safe specifically because Google guarantees `email_verified`.
- `db/schema.sql`: added nullable `users.google_sub text unique` (+ migration `alter table ... add column if not exists`).
- Frontend (`data-layer.js`): loads `accounts.google.com/gsi/client` lazily, only if `config.js` sets `googleClientId` (falls back to email-only, matching the existing "absent config.js = fully local" pattern). New `google-signin-container`/`cloud-sync-divider` elements in `index.html`, styled in `styles.css`.
- New env var `GOOGLE_CLIENT_ID` (server) must match `config.js`'s `googleClientId` (client) — documented in README and `config.example.js`. Both are the public OAuth client ID, not a secret.

**Verified in this sandbox:** `node --check` + `npm run lint` clean on all touched files; `npm run build` still succeeds; `server.js` boots and correctly returns 400 (missing credential), 500 (missing `GOOGLE_CLIENT_ID`), 401 (malformed token) and 405 (wrong method) from `/api/auth/google`; confirmed outbound reachability to Google's JWKS endpoint.

**2026-09-11, same day — real bug found after the user tested manually:** clicking "Continuer avec Google" and picking an account returned "Erreur : Jeton Google invalide ou expiré." Root cause (from the real server log, not guesswork): `column "google_sub" does not exist` — the column was added to `db/schema.sql` but `npm run apply-schema` was never actually run against the real Neon DB after that (exactly the gap flagged as "not verified" in the first pass of this memory, below). Fixed by running `npm run apply-schema` (39/39 statements applied). Verified via a direct query that `users.google_sub` now exists and that both test accounts (`thierry1804@gmail.com`, `trandriantiana@gmail.com`) got real rows with `google_sub` populated after retrying. **Lesson: a schema change checked into `db/schema.sql` is not live until `apply-schema` is actually run against the target DB — code review / lint / local syntax checks cannot catch this, only a real request against the real DB surfaces it.** Always ask "was apply-schema actually run against prod?" as a first check when a Neon-backed endpoint fails right after a schema change.

**2026-09-11, later same day — added name/profile-picture capture.** User asked to also surface the Google account's name/email/photo (previously only email was stored). Added `users.name` / `users.picture_url` columns (nullable, migrated via `apply-schema`); `api/auth/google.js` now reads `payload.name`/`payload.picture` from the already-verified ID token (default `openid email profile` scope — no extra scope needed) and upserts them on every login (kept fresh); `api/auth/verify.js` (magic link) also returns any previously-stored name/picture so switching login methods doesn't lose it. Client (`data-layer.js`) stores `name`/`picture` in the persisted session object and renders the photo via `document.createElement('img')` (never innerHTML string interpolation, even though the URL is server-verified) into both the compact "Cloud & synchronisation" card and the main `#user-avatar` profile header — safe to touch `#user-avatar` because `app.js`'s `showUserProfile()` only ever sets the name/email text nodes there, never the avatar markup, so there's no re-render race. Verified end-to-end in a real browser: after re-login, `trandriantiana@gmail.com`'s row got `name: "Thierry Randriantiana"` and a picture URL, both rendered correctly in the UI.
